One task. Four accountable moments.

Agent sessions come and go. Loomrail keeps the durable route around them, so progress is a sequence of explicit state changes instead of a persuasive chat transcript.

  1. 01

    Define what done means

    A WorkItem carries the brief, acceptance criteria, workflow version, permissions, and budget.

    Output → versioned task contract
  2. 02

    Decide at the real fork

    Questions and approvals become typed Human Requests. Your answer is stored as a durable Decision.

    Output → attributable decision
  3. 03

    Verify the repository change

    Review and QA produce typed evidence against criteria while the work stays isolated in its worktree.

    Output → inspectable evidence matrix
  4. 04

    Accept as the owner

    Done is not an agent claim. Acceptance is a separate owner-only event with an auditable package.

    Output → acceptance package + event

The board is the index. The task is the cockpit.

The Workbench keeps current state compact, then opens the evidence, criteria and activity behind it. Raw provider logs remain diagnostic data, not the primary product surface.

Useful now. Explicit about what is not.

This is an early public checkpoint, not a finished desktop product. The boundary below is part of the contract, not fine print.

Runtime
Today: loopback daemon, authenticated browser session, local SQLite state.
Providers
Today: Codex across six stages; Claude Code for Discovery, Plan and Review.
Repository
Today: per-task Git worktree and on-demand diff visibility.
After the edit
Not today: Loomrail does not commit, push, merge or deploy.
Platforms
Blocking: macOS and Windows. Linux remains best effort.
Distribution
Not today: desktop installer, remote mode, cloud sync and plugins.

Start locally in two commands.

Requires Node.js 24.19.x on macOS or Windows. The launcher opens a one-time authenticated URL on loopback; add --no-open to print it instead.
