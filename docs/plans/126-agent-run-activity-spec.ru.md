# Agent Run Activity — уровень 1: спецификация

**Статус:** approved; implemented ([ADR-0034](../adr/0034-diagnostic-provider-activity.md))

**Основание:** UXD-002, UXD-003, PD-006, PD-020, AD-005, SD-003, SD-004, AGENTS.md (UI: raw provider logs —
diagnostic view).

Утверждение THREAT-MODEL §Q7 «raw provider stdout/stderr remains deliberately unrecorded» остаётся истинным: уровень 1
не записывает сырой поток. Но это новая capability, которая меняет утверждённую границу — адаптеры сегодня
намеренно отбрасывают эти события, и в `provider-codex/src/stream.ts` для этого записан явный rationale. Поэтому
работа требует ADR на изменение границы и дельты THREAT-MODEL, а не только кода.

## Outcome

Владелец видит, что агент делает прямо сейчас, и что он делал в завершённом прогоне. В Task Cockpit появляется
секция Run Activity: последовательность выполненных действий — какие команды запускались, какие файлы читались и
правились, что агент написал о своей работе. В Agent Fleet появляется одна колонка с последним действием каждого
активного прогона. Во время работы лента обновляется без перезагрузки страницы; после завершения остаётся
доступной для разбора.

Лента сводит в одну хронологию два источника: действия, выполненные через daemon-owned workspace tools и уже
записанные в `workspace_tool_calls` (ADR-0014), и действия, о которых провайдер отчитался сам. Владелец видит один
связный рассказ о прогоне, а не две пересекающиеся ленты.

Лента ничего не доказывает. Она объясняет.

## Архитектурная граница

`AgentRunActivity` — bounded диагностическая проекция того, что провайдер сообщил о себе. Источником правды о
результате работы остаются `git diff` по worktree, measured verification и domain-owned Acceptance. PD-020
сохраняется без изменений: провайдер не именует evidence и не объявляет факты Acceptance, а лента не даёт ему такой
возможности задним числом.

Захват живёт в provider adapter, потому что форма событий провайдер-специфична (архитектурное правило: provider
payload не покидает адаптер). Наружу адаптер отдаёт уже нормализованную запись через новый опциональный callback
`ProviderSessionListener.onActivity`. Domain о ленте не знает и на неё не смотрит.

AD-005 сохраняется: запись несёт поле `provider`, и UI не притворяется, что «выполненная команда» у Codex и
«вызванный инструмент» у Claude Code — одно и то же понятие.

Два источника ленты имеют разную authority, и это различие обязано остаться видимым. Действие, прошедшее через
daemon-owned gateway, проверено Loomrail, живёт в append-only `workspace_tool_calls` и неудаляемо. Действие, о
котором отчитался провайдер, не проверено ничем, прунится и ничего не доказывает. Поэтому хранение остаётся
раздельным — новая таблица не смешивается с авторитетным аудитом ADR-0014 — а объединение происходит на чтении, и
каждая запись несёт `origin`.

Записи `WORKSPACE_TOOL_CALL_CHANGED` перестают отображаться в общей Activity ленты WorkItem и переезжают в Run
Activity. Activity остаётся историей жизненного цикла работы, Run Activity — рассказом о том, что делал агент.
Одно действие показывается ровно в одном месте.

Доставка идёт существующим механизмом: кадр канала событий остаётся тремя непрозрачными идентификаторами, клиент по
сигналу дотягивает содержимое обычным authenticated HTTP. Контракт `eventSignalSchema` не расширяется.

## Контракт

Запись ленты:

- `seq` — монотонный integer в пределах одного прогона, начинается с 1;
- `at` — момент записи строки по инжектированным часам state store, а не момент, когда провайдер отчитался:
  запись выполняет дренаж вне горячего пути, поэтому `at` отстаёт от отчёта на интервал дренажа (250 мс) плюс
  время ожидания в очереди. Для диагностической ленты этой точности достаточно, и большей она не обещает;
- `provider` — `CODEX | CLAUDE_CODE`;
- `origin` — `DAEMON_AUDITED | PROVIDER_REPORTED`; у записей новой таблицы он всегда `PROVIDER_REPORTED`, у записей
  из `workspace_tool_calls` — всегда `DAEMON_AUDITED`; поле вычисляется источником, а не принимается от провайдера;
- `kind` — `TOOL_CALL | AGENT_TEXT | FILE_CHANGE | PROVIDER_ERROR`;
- `label` — не более 500 символов после redaction;
- `detail` — не более 2 000 символов после redaction, либо `null`;
- `status` — bounded строка результата либо `null`.

Отображение провайдерских событий:

| Провайдер   | Событие                        | `kind`           | `label`                    | `detail`                        | `status`          |
| ----------- | ------------------------------ | ---------------- | -------------------------- | ------------------------------- | ----------------- |
| Codex       | `command_execution`            | `TOOL_CALL`      | команда                    | —                               | exit code         |
| Codex       | `file_change`                  | `FILE_CHANGE`    | путь относительно worktree | остальные пути того же действия | —                 |
| Codex       | `agent_message`                | `AGENT_TEXT`     | —                          | текст                           | —                 |
| Codex       | `turn.failed` (не реализовано) | `PROVIDER_ERROR` | типизированная причина     | —                               | —                 |
| Claude Code | `tool_use`                     | `TOOL_CALL`      | имя инструмента            | извлечённая цель                | —                 |
| Claude Code | `tool_result`                  | `TOOL_CALL`      | —                          | —                               | успех либо ошибка |
| Claude Code | `text` block                   | `AGENT_TEXT`     | —                          | текст                           | —                 |

Строка `turn.failed → PROVIDER_ERROR` в уровне 1 **не реализована**. `kind` `PROVIDER_ERROR` объявлен в контракте,
в `CHECK` таблицы и в i18n, но ни один парсер его не порождает: `parseCodexActivity` читает только `item.started`
и `item.completed`. Строка оставлена в таблице как описание намерения, а не кода; фактически лента уровня 1 несёт
только `TOOL_CALL`, `FILE_CHANGE` и `AGENT_TEXT`. Отказ turn'а по-прежнему виден через исход сессии, а не через
ленту.

`detail` у `file_change` содержит остальные пути того же действия (через запятую), а не вид изменения:
`change.kind` разбирается схемой, но в запись не попадает.

Одно действие провайдера даёт ровно одну запись. Провайдер сообщает о действии дважды — началом и завершением
(`item.started` / `item.completed` у Codex, `tool_use` и парный `tool_result` у Claude Code). Запись создаётся на
первом событии и обновляется на терминальном по идентификатору действия, который провайдер несёт сам; вторая запись
не появляется. Действие, завершения которого не пришло, остаётся с `status = null` и читается как незавершённое —
это честное состояние, а не дефект.

Правила захвата:

- из `tool_use.input` извлекается одно целевое значение по имени инструмента; произвольный JSON аргументов в ленту
  не попадает;
- `tool_result.content` не сохраняется: из него берётся только признак успеха и, если есть, bounded код ошибки;
- `command_execution.aggregated_output` не сохраняется на этом уровне;
- `file_change.changes` даёт только пути относительно worktree, без содержимого; вид изменения не записывается;
- всё, что попадает в `label` и `detail`, проходит через `sanitizeSupervisedOutput` из `@loomrail/process-supervision`
  с тем же набором redaction values, который уже применяет workspace executor; второй санитайзер не создаётся;
- `system`-события Claude Code, включая hook stdout/stderr, по-прежнему отбрасываются целиком до захвата (SD-003);
- путь, который после redaction и нормализации выходит за пределы worktree, записывается как непрозрачная отметка, а
  не как абсолютный путь;
- текст, не поместившийся в границу `label` или `detail`, усекается по границе кодовой точки (границы контракта
  заданы в символах, и разрез посреди суррогатной пары дал бы порчу, неотличимую от вывода провайдера) и
  помечается как усечённый; молчаливого обрезания нет;
- на один прогон хранится не более 1 000 записей; при переполнении вытесняются самые ранние, а `omittedCount`
  прогона растёт и показывается владельцу явно;
- вытеснение делает `seq` разреженным: он остаётся монотонным и пригодным как курсор, но не плотным, и клиент не
  вправе считать пропуск номера дефектом.

Диагностические счётчики адаптеров `linesUnused` и `linesUnreadable` пересматриваются вместе с парсерами: события,
которые теперь читаются, перестают учитываться как неиспользованные. Счётчик, срабатывающий на каждом успешном
прогоне, не является сигналом.

## Интерфейс

- `GET /api/v1/agent-runs/:runId/activity?after=<cursor>` — authenticated, возвращает объединённую страницу записей
  обоих источников, `omittedCount` и признак `degraded`; слияние выполняется на сервере, чтобы у клиента был один
  курсор и один порядок, а не два independently paginated списка;
- порядок детерминирован: по `at`, затем по `origin`, затем по идентификатору записи; одинаковые метки времени не
  дают нестабильной выдачи;
- `cursor` непрозрачен: клиент передаёт его обратно и не разбирает; `seq` новой таблицы не является курсором
  объединённой ленты;
- курсор, указывающий на уже вытесненную запись, обслуживается как запрос с начала доступного окна и сопровождается
  признаком разрыва, а не молчаливой выдачей неполного хвоста;
- сигнал канала событий публикуется с дебаунсом: болтливый прогон не превращается в поток сигналов;
- Task Cockpit — секция Run Activity, по умолчанию свёрнута до последнего действия и счётчика, раскрывается по
  действию владельца (UXD-002); она не становится основным содержимым Cockpit;
- происхождение записи различимо без цвета: проверенное Loomrail действие и отчёт провайдера читаются как разные
  вещи, и владельцу доступно объяснение разницы;
- Agent Fleet остаётся таблицей и получает одну колонку последнего действия; сетка карточек не вводится (UXD-003);
- статус записи различим без цвета; светлая и тёмная темы равноправны; клавиатурная навигация и видимый фокус
  реализуются вместе с первой версией;
- текст ленты рендерится как текст: Markdown, HTML и ссылки из вывода провайдера не интерпретируются.

## Надёжность и деградация

Запись ленты не имеет права бросить исключение в `onLine`. В `runProcess` листенер обёрнут в `guarded`: брошенное
исключение останавливает дочерний процесс и приводит к отказу сессии. Диагностика не может ломать то, что
диагностирует.

Поэтому recorder работает best-effort: копит записи в ограниченный буфер в памяти и пишет их вне горячего пути. При
любой ошибке записи прогон продолжается, лента помечается `degraded`, и владелец видит эту отметку. Потеря ленты
никогда не влияет на исход прогона, на usage, на checkpoint и на Acceptance.

## Recovery и совместимость

- additive SQLite migration версии 62; существующие прогоны имеют пустую ленту;
- запись ленты не участвует в транзакции, которая фиксирует state, Event и durable follow-up, и не может её
  заблокировать;
- после restart демона уже записанная лента читается без изменений; незавершённый буфер прогона, прерванного
  падением, теряется и лента помечается `degraded`;
- retention: единственное, что сегодня ограничивает ленту, — это предел в 1 000 записей на прогон с вытеснением
  самых ранних. Свёртки по возрасту нет: ни один существующий cleanup не удаляет строки `agent_run_activity`, и
  30-дневная свёртка незакреплённых диагностических данных по SD-004 на эту таблицу **не реализована**. Пока она
  не сделана, локальная база держит до 1 000 записей на каждый AgentRun бессрочно. Реализация — отдельная работа
  со своими тестами, вне этого уровня;
- `onActivity` опционален в `ProviderSessionListener`, как `onAllowance` и `onProcessStarted`; адаптер, который его
  не вызывает, остаётся корректным;
- macOS и Windows используют одинаковые семантику и границы; фикстуры включают пробелы и не-ASCII.

## Non-goals

- уровень 2 — сырой поток провайдера в файловых сегментах и его owner opt-in; отдельная работа, отдельный ADR;
- extended thinking у Claude Code и отображение цепочки рассуждений; режим запуска не меняется;
- ввод в провайдерскую сессию из UI; лента доступна только на чтение, чат не вводится (PD-006);
- участие ленты в Acceptance, evidence package, reporting export, insights payload и crash payload;
- экспорт ленты, отправка её куда-либо за пределы loopback и любая телеметрия (SD-003);
- превращение Agent Fleet в сетку карточек;
- лента как источник факта о том, что изменилось в репозитории.

## Acceptance

1. Парсеры обоих провайдеров строят ожидаемые записи на уже имеющихся записанных потоках
   (`workspace-write.jsonl`, `claude-2.1.260-mcp-macos-arm64.jsonl`); живой прогон и расход квоты для этого не нужны.
2. Канареечный секрет, встречающийся в команде, в аргументе инструмента и в пути, отсутствует в HTTP-ответе, в
   SQLite и в логах.
3. Writer, бросающий исключение на каждой записи, не влияет на исход прогона: сессия завершается штатно, лента
   помечена `degraded`, usage и checkpoint не изменились.
4. Прогон, произведший больше 1 000 записей, отдаёт последние 1 000 и честный `omittedCount`; молчаливой потери нет.
5. Существующие leak-сканы acceptance, evidence package, reporting, insights и crash payload остаются зелёными;
   добавлены канарейки именно на содержимое ленты.
6. `system`-события Claude Code, включая hook-события, не попадают в ленту ни при каких входных данных.
7. Диагностические счётчики адаптеров не растут на успешном прогоне, события которого теперь читаются.
8. Кадр канала событий не изменился; E2E доказывает живое обновление ленты через сигнал и дотягивание.
9. UI-секция и колонка Fleet проверены в светлой и тёмной темах, с клавиатуры, со статусом, различимым без цвета;
   враждебный bounded-текст из вывода провайдера рендерится как текст.
10. Объединённая лента отдаёт оба источника в детерминированном порядке; одинаковые метки времени не меняют выдачу
    между запросами; `origin` каждой записи соответствует её источнику.
11. Одно действие через workspace tool появляется в Run Activity ровно один раз и больше не дублируется в Activity
    ленте WorkItem.
12. ADR на изменение границы принят, дельта THREAT-MODEL описывает capability и её verification, и ни один
    документ релиза не противоречит коду.
13. Focused tests, product E2E и полный `pnpm verify` проходят.
