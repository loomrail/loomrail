## 1. Проблема

README отвечает на вопрос «что такое Loomrail» и одновременно пытается быть инструкцией для разработчика,
релизера и первого пользователя. Из него можно собрать отдельные команды, но нельзя пройти один непрерывный путь:

1. установить и безопасно открыть локальную сессию;
2. понять, mock или живой провайдер сейчас работает;
3. зарегистрировать настоящий репозиторий;
4. создать задачу и довести её через Human Request, бюджет и acceptance;
5. увидеть результат в worktree и сохранить состояние перед переносом или резервным копированием.

Для второй persona из PD-007 это превращает существующий продукт в набор внутренних терминов. Для опытного
разработчика опаснее другое: README не собирает в одном месте границы полномочий Git и резервного копирования, поэтому
легко принять migration-backup SQLite за полный backup или решить, что Loomrail уже коммитит результат.

---

## 2. Результат D1

D1 создаёт две самостоятельные инструкции:

- `docs/guides/USER-GUIDE.md` — английская, основная публичная версия;
- `docs/guides/USER-GUIDE.ru.md` — русская версия того же маршрута.

Обе должны быть пригодны для последовательного чтения с нуля и содержать взаимную ссылку в первой экранной области.
README остаётся краткой точкой входа и ссылается на обе версии; он не дублирует весь маршрут.

D1 не добавляет новый runtime API, не меняет Git-authority и не превращает pre-alpha в опубликованный продукт.

---

## 3. Решения

### D1 — Первый успешный запуск начинается с mock

Гайд сначала проводит владельца через deterministic mock. Это проверяет установку, локальную сессию, durable workflow,
Human Request, budget override и acceptance без запуска внешнего CLI и без расхода его лимита. Живой Codex — отдельный
следующий шаг на репозитории, который владелец выбрал явно.

Mock всегда называется mock. Общая кнопка запуска и название workflow в интерфейсе при этом не должны утверждать, что
запускается mock: тот же шаблон реально диспетчеризует Codex или Claude Code. D1 исправляет устаревшие подписи на
нейтральные «Start workflow» / «Delivery workflow» и русские эквиваленты.

### D2 — Установка описывает текущий артефакт, а не будущий npm publish

До первой публикации поддержан tarball из `pnpm pack:release`. Гайд не использует ещё не существующую команду
`npm install loomrail` и не обещает desktop installer. Запуск из исходников остаётся явно помеченным путём
контрибьютора.

Имя tarball содержит версию. В инструкции используется `<version>` и отдельно сказано взять фактическое имя из
`dist-release/`, а не копировать текущую `0.0.0` как вечный контракт.

### D3 — Bootstrap-ссылка локальна, одноразова и не является remote mode

Daemon слушает loopback. `--no-open` печатает ссылку для браузера **на той же машине**; это не удалённый доступ.
Ссылка действует 60 секунд, входит ровно один браузер и заменяется при каждом рестарте. Закрытие вкладки не останавливает
daemon или очередь; `Ctrl+C` в терминале завершает процесс штатно.

### D4 — Провайдер назван до первого запуска задачи

Гайд показывает `MOCK`, `CODEX` и `CLAUDE_CODE`, точные регистрозависимые значения `LOOMRAIL_PROVIDER`, различие
macOS shell и Windows PowerShell и текущие capabilities:

- mock — все шесть стадий, реальный агент не запускается;
- Codex — все шесть стадий в worktree;
- Claude Code — только Discovery, Plan и Review; неподдержанная стадия становится Human Request.

Неизвестное значение откатывается к mock с предупреждением. CLI провайдера устанавливается и аутентифицируется самим
владельцем; Loomrail не принимает его credentials.

### D5 — Регистрация репозитория объясняет реальную границу

Путь должен быть абсолютным путём к корню Git-репозитория с хотя бы одним commit. Перед первой агентской стадией
Loomrail создаёт carry-in snapshot, отдельную ветку `loomrail/...` и linked worktree в data directory. Незакоммиченные
и неигнорируемые файлы владельца попадают в snapshot. Агент работает с сетью и правами владельца; worktree — изоляция
от случайных Git-коллизий, не security sandbox.

Loomrail не коммитит результат агента, не push-ит и не merge-ит его. Карточка показывает только наблюдение: workspace,
изменённые файлы и запрошенный владельцем diff.

### D6 — Основной маршрут следует интерфейсу

Обе версии гайда проводят один и тот же маршрут:

1. Project → New task → brief;
2. acceptance criteria через Edit task;
3. Move to Ready → Start workflow;
4. ответ на blocking Human Request;
5. Pause/Resume и budget override только там, где соответствующее действие действительно доступно;
6. Review/QA evidence, criterion matrix и решение Acceptance;
7. Changes и путь worktree до окончательного решения владельца.

Return to work, Reject и Cancel называются как альтернативы, но гайд не изображает из них полностью проверенный
happy-path. Полный воспроизводимый live-сценарий принадлежит D2.

### D7 — Restart и backup не смешиваются

Restart — обычное открытие той же durable SQLite state: новый bootstrap, те же задачи, Human Requests и события.
Прерванная provider session не оживает как процесс; Loomrail согласует состояние и продолжает из durable context или
показывает Recovery report/Resume.

Сохранение состояния — отдельная операция:

1. штатно остановить Loomrail;
2. копировать **весь** data directory, а не один `state.sqlite` во время WAL-записи;
3. восстанавливать его в то же расположение при остановленном Loomrail;
4. отдельно сохранять исходные Git-репозитории.

`backups/` содержит online backup перед миграцией и не является расписанием резервного копирования. Data directory
содержит SQLite, materialized demo repositories и worktrees, но linked worktree зависит от Git metadata исходного
репозитория и абсолютного пути. Поэтому единственная надёжная переносимая копия незакоммиченного результата — та,
которую владелец сам сохранил из показанного worktree; D1 не приписывает Loomrail отсутствующий commit/export.

### D8 — Ограничения стоят рядом с действием

Pre-alpha ограничения не прячутся в финальный disclaimer. Каждое опасное ожидание опровергается там, где возникает:

- у установки — пакет ещё не опубликован;
- у bootstrap — только та же машина;
- у live provider — owner privileges, network и неполный Claude write path;
- у worktree — не sandbox и не Git backup;
- у acceptance — Loomrail не commit/push/merge;
- у state preservation — нет поддержанного online export/restore UI.

## 4. Информационная архитектура гайда

1. статус и границы pre-alpha;
2. установка tarball и запуск из исходников;
3. локальная сессия и остановка;
4. выбор provider;
5. первый mock-маршрут;
6. регистрация настоящего репозитория и live-маршрут;
7. Human Requests, budgets, pause и acceptance;
8. просмотр изменений;
9. restart и recovery;
10. data directory, backup и restore;
11. troubleshooting и текущие ограничения.

Разделы могут объединяться ради читаемости, но ни один из перечисленных фактов не может исчезнуть.

---

## 5. Проверка

### Автоматические гейты

- `pnpm verify` — формат, public-tree safety и тесты подписи workflow;
- `pnpm pack:release && pnpm test:release` — описанный tarball действительно ставится в чистое временное окружение;
- `pnpm test:e2e` — названные действия mock-маршрута, restart, Human Request, budget, acceptance и Changes существуют.

### Ручная документальная проверка

- каждая локальная Markdown-ссылка разрешается относительно своего файла;
- команды не требуют неопубликованного пакета или отсутствующего `--help`;
- английский и русский гайды имеют одинаковые смысловые разделы;
- ни один текст не называет loopback remote mode, migration backup полным backup или worktree sandbox;
- README ведёт в гайд до contributor-only разделов.

---

## 6. Критерии приёмки

1. Новый пользователь может пройти mock-маршрут от tarball до Accepted, не читая implementation plans.
2. Пользователь Codex понимает до запуска, какой репозиторий и с какими правами увидит агент.
3. Пользователь Claude Code заранее знает, что Implementation и QA не исполняются этим адаптером.
4. После restart пользователь знает, что сохранено, где взять новый вход и чем interrupted session отличается от
   потерянной задачи.
5. Инструкция сохранения состояния не предлагает копировать live `state.sqlite` и не обещает переносимость linked
   worktree без исходного репозитория.
6. Гайд не утверждает, что Loomrail commit-ит, push-ит, merge-ит, публикуется из npm или имеет desktop/remote mode.
7. Обе языковые версии и ссылки из README проходят проверки §5.

---

## 7. Не входит в D1

- новый onboarding UI или walkthrough;
- кнопка backup/export/restore;
- автоматический Git commit, squash, push или merge;
- скриншоты и маркетинговая страница — D3;
- отдельный воспроизводимый live fixture и готовые артефакты маршрута — D2;
- публикация npm-пакета или desktop installer;
- remote access, cloud sync и multi-user режим.
