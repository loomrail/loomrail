# A1 — Session handoff и непрерывность работы агента

**Дата:** 2026-08-25
**Статус:** design approved владельцем; implementation plan ещё не написан
**Нормативные входы:**

- [Product decisions](../product/PRODUCT-DECISIONS.ru.md) — PD-008 (handoff проектируется до живых провайдеров)
- [Master plan](../product/MASTER-PLAN.ru.md) — §5.2 (сущности), §7.3 (role profile contract), §7.4
  (artifact-driven collaboration), §8.2 (policy precedence), §8.3 (storage split)
- [Декомпозиция работ после Phase 0](06-post-phase-0-decomposition.ru.md) — порядок M7 → **A1** → A2 → E1 → …
- [Threat model](../security/THREAT-MODEL.md)

Этот документ проектирует одну подсистему: пересборку контекста исполнения из состояния, которым Loomrail уже
владеет. Он не проектирует живые адаптеры (A2), доступ к файловой системе (E1) и роли (A3), но фиксирует
контракты, на которые они обязаны лечь.

## 1. Задача

Сегодня Loomrail durable по состоянию: WorkItem, стадии, попытки, бюджеты, evidence, Decisions и Event переживают
рестарт демона. Контекст исполнения агента не хранится нигде.

С mock-провайдером это незаметно: вызов провайдера — одна короткая функция, и «контекст» умещается в её
аргументы. С живым провайдером стадия IMPLEMENT превращается в длинную сессию, которая упирается в лимит окна
посреди работы. В этот момент продолжать нечем: история диалога Loomrail не принадлежит, а состояния, из которого
можно собрать новый вход, в нужной форме не существует.

PD-008 фиксирует, что handoff — **не перенос истории диалога**, а пересборка нового входа из состояния, которым
Loomrail владеет. Отсюда два следствия, определяющие весь дизайн: handoff переживает смену провайдера, и он
обязан быть спроектирован до A2, иначе адаптеры придётся переделывать под контракт, которого на момент их
написания не существовало.

## 2. Принятые решения

Восемь решений, зафиксированных владельцем при проработке дизайна. Каждое меняет форму контрактов, поэтому
пересмотр любого из них требует пересмотра спека, а не правки реализации.

### D1 — Handoff это единственный способ запуска

Каждый вызов провайдера получает контекст, собранный из durable state. «Продолжение» — это новая сборка с
обновлённым входом, а не особый режим.

**Почему.** Отдельный путь «только при исчерпании контекста» означал бы два пути исполнения в каждом адаптере,
причём редко исполняемый путь — тот, который обязан сработать в самый неудобный момент. Единственный путь
проверяется каждым тестом.

**Следствие.** `resume` исчезает из контракта адаптера (см. §5).

### D2 — Прогресс внутри попытки поставляет агент, публикуя checkpoint

Работа считается существующей только после записи в durable state. Публикация checkpoint — часть контракта роли
(§7.3 мастер-плана).

**Почему.** Альтернатива «попросить агента подвести итог перед handoff» не работает ровно в целевом сценарии
PD-008: если сессия уже упёрлась в лимит или умерла, спрашивать некого. Альтернатива «вывести прогресс из
рабочего дерева» требует E1, который идёт после A2, и не восстанавливает намерение — из диффа не видно, почему
сделано так.

**Принятая цена.** Хвост между последним checkpoint и обрывом теряется. Дизайн делает эту потерю видимой
(§6.3 и §7), а не маскирует её.

### D3 — Pack содержит собранное содержимое, а не ссылки

Loomrail собирает готовый вход. Стадия объявляет секции и их порядок, при переполнении урезание идёт с конца и
записывается в рецепт.

**Почему.** Вариант со ссылками, которые агент дотягивает сам, требует инструмента доступа к состоянию — это C1,
идущий сильно позже, — и разрушает аудируемость: становится неизвестно, что реально было в контексте. §5.2 уже
определяет `PolicySnapshot` как «точный context/policy конкретного run», то есть мастер-план исходит из того, что
Loomrail знает точный контекст запуска.

### D4 — Состав объявляется по цепочке precedence §8.2

`Workflow template > Role playbook > Task instructions`, где нижний слой уточняет верхний, но не ослабляет его.
В v1 заполнен только слой workflow template — единственный существующий. A3 добавит слой role playbook как
уточнение: роль сможет добавить секцию и поднять её приоритет, но не сможет убрать объявленное шаблоном
обязательным.

**Почему это не требует переупорядочивания работ.** Декларация состава никогда не пересекает границу адаптера:
адаптер получает собранный pack, а не рецепт его сборки. Пока это так, вопрос «кто объявляет» полностью
внутренний для Loomrail, и слой роли добавляется в A3 без изменения контракта и без переписывания адаптеров.

**Принятая цена.** A1 фиксирует форму слоя, у которого ещё нет потребителя. Если в A3 окажется, что роли нужно
выражать что-то, чего `ContextPackSpec` не умеет, это будет миграция шаблонов, а не переделка адаптеров.

### D5 — Единица перезапуска это `ProviderSession` внутри того же `StageAttempt`

`StageAttempt` остаётся единицей работы, `ProviderSession` — единицей исполнения.

**Почему.** `stageAttemptStatus` уже содержит `INTERRUPTED`, `RECOVERING`, `FAILED`: attempt семантически значит
«попытка, которая чем-то кончилась». Штатная пересборка контекста — не отказ. Смешав их, мы получили бы доску,
где здоровая длинная задача выглядит трижды упавшей, и метрики надёжности, в которые записан шум. Бюджет при
таком разделении суммируется по attempt естественно.

**Принятая цена.** Появляется вложенность, которой сейчас нет. Её обязан показывать Task Cockpit, иначе
исчерпание контекста станет невидимым.

### D6 — Рез превентивный, с реактивным как записанной аварийной ветвью

Провайдер — единственный источник истины о занятости окна и сообщает её. Порог и решение принадлежат Loomrail.
При пересечении порога сессия помечается сворачивающейся; рез происходит **в первой точке checkpoint после
порога**, а не в момент порога.

**Почему.** Резать по факту стены — значит гарантированно терять хвост каждый раз. Резать ровно на пороге —
значит переносить ту же потерю на более ранний момент. Раскладка «провайдер сообщает, Loomrail решает»
повторяет уже работающий бюджет токенов: `usageQuality` различает `ACTUAL | PROVIDER_ESTIMATE |
LOOMRAIL_ESTIMATE`, есть пороговые события и SOFT/HARD-пауза.

Реактивная ветвь остаётся: стена случится на неверной оценке или на внезапно длинном ответе. У неё определённый
исход, записанный в Event, а не вид зависшей стадии.

### D7 — Для аудита сохраняется рецепт сборки и хеш, а не текст pack

Рецепт хранит список секций с источниками (`id` + `version`) и хеш собранного текста.

**Почему.** Хранение полного текста дублировало бы бриф и план в каждую сессию, а сессий с живыми провайдерами
будет много. Рецепт мал, воспроизводим, а хеш делает подмену обнаружимой.

**Несущее условие.** Pack имеет право ссылаться только на immutable-версии. Event уже append-only, `Checkpoint`
по этому спеку append-only и редактированию не подлежит. Если бы источники можно было молча править, врал бы и
вариант с полным текстом — просто менее заметно.

### D8 — Переполнение обязательного ядра это HARD-пауза и Human Request

Если обязательные секции не влезают даже после урезания всего необязательного, сессия не стартует.

**Почему.** §8.2: «неустранимый конфликт создаёт Human Request». Механизм HARD-паузы уже существует для бюджета.
Урезать обязательное с записью в Event — значит выдать агенту вход, про который система знает, что он неполный,
и продолжить как ни в чём не бывало.

**Будущее уточнение.** Не влезающее ядро — почти всегда симптом того, что WorkItem слишком крупный. Тогда
правильный вопрос владельцу не «что делать?», а «разбить вот так?». Механизм паузы и Human Request тот же,
меняется только содержание вопроса, поэтому это дешевле добавить позже, чем угадать сейчас.

## 3. Границы и пакеты

Новый пакет `packages/context-assembly` с одной публичной функцией:

```text
assembleContextPack({ sources, spec, budget }) → { pack, recipe, omissions }
```

Инфраструктуры не знает, SQLite не касается, зависит только от `@loomrail/contracts`. Детерминирован по
построению: те же входы дают тот же байт-в-байт текст и тот же хеш.

Детерминизм — проверяемое утверждение, поэтому его условия фиксируются здесь, а не оставляются реализации:
рендер даёт UTF-8 с `LF`, `contentHash` — SHA-256 от этих байт с явным префиксом алгоритма (`sha256:`). Без
зафиксированной кодировки тест «рецепт воспроизводит pack» зелёный на macOS и красный на Windows.

Отдельный пакет, а не функция в `packages/domain/src/workflow.ts`: тот файл уже превышает 1300 строк и держит
принятие решений о состоянии. Сборка контекста — другая ответственность с собственным словарём (секции,
приоритеты, урезание, оценка размера), и она будет расти. Это «deep module with a small public contract» из
AGENTS.md, а не ещё одна обёртка.

| Слой                 | Роль                                                                             |
| -------------------- | -------------------------------------------------------------------------------- |
| `contracts`          | схемы `ContextPackSpec`, `ContextPack`, `ContextPackRecipe`, `Checkpoint`, usage |
| `workflow-engine`    | `validateContextPackSpec` по образцу `validateWorkflowTemplate`                  |
| `context-assembly`   | сборка, урезание по порядку, оценка размера                                      |
| `persistence-sqlite` | читает срез в `ContextSources`; пишет рецепт, сессию и Event одной транзакцией   |
| `domain`             | решает, когда резать сессию и когда поднимать HARD-паузу                         |
| адаптер (A2)         | получает готовый `ContextPack`; декларации не видит никогда                      |

## 4. Модель данных

### 4.1. Декларация состава

`workflowTemplateStage` получает поле `contextPack`:

```text
ContextPackSpec     { schemaVersion, sections: [ContextPackSection] }   // ≥ 1 секция
ContextPackSection  { id, ordinal, required }
```

Один ординал обслуживает и порядок отрисовки, и порядок урезания: важное идёт первым и отбрасывается последним.
Отдельный enum приоритетов не нужен — `required` задаёт пол, ординал задаёт всё остальное.

`validateContextPackSpec` требует непрерывных ординалов с нуля, уникальных `id` и хотя бы одной обязательной
секции. Это тот же контракт, что у `validateWorkflowTemplate`, и он должен жить рядом с ним.

Секции v1 — только то, чем состояние уже владеет:

`WORK_ITEM_BRIEF`, `WORKFLOW_POSITION`, `DECISIONS`, `LATEST_CHECKPOINT`, `EVIDENCE`, `ACTIVITY`.

Диффов рабочего дерева здесь нет и быть не может: это E1.

Шаблон `mock-delivery-v1` переходит с версии 2 на 3, то есть путь миграции шаблонов прогоняется по-настоящему.
Покрытие уже существует: `starts the current workflow after a legacy template version was persisted`.

### 4.2. Новые сущности

```text
ProviderSession    { id, stageAttemptId, ordinal, status, endReason,
                     contextPackRecipeId, startedAt, endedAt, version }

                     endReason: COMPLETED | HANDOFF | CONTEXT_EXHAUSTED
                              | INTERRUPTED | CANCELLED

ContextPackRecipe  { id, providerSessionId, templateId, templateVersion,
                     specSource: WORKFLOW_TEMPLATE,        // A3 добавит ROLE_PLAYBOOK
                     sections: [{ id, sources: [{ kind, id, version }], bytes }],
                     omitted:  [{ id, reason: CONTEXT_BUDGET }],
                     contentHash, estimatedTokens, budgetTokens, estimateQuality }

Checkpoint         { id, stageAttemptId, providerSessionId, ordinal, summary,
                     completed[], remaining[], deadEnds[], openQuestions[], createdAt }
```

`Checkpoint` append-only и редактированию не подлежит — это несущее условие D7, а не аккуратность.

Происхождение секции — **список**, а не одна пара. Три секции из шести (`DECISIONS`, `EVIDENCE`, `ACTIVITY`)
представляют коллекции записей, у каждой свой `id` и своя версия. Одной парой их не выразить, а секция без
записанного происхождения делает утверждение D7 ложным, оставляя рецепт заполненным на вид. Мощность списка
несёт смысл: 0 — секция производная, 1 — одна durable-сущность, N — коллекция. У `WORKFLOW_POSITION` список
пуст законно: `templateId` и `templateVersion` записаны на верхнем уровне рецепта.

`deadEnds` присутствует намеренно: без него следующая сессия повторит тупик, из которого предыдущая уже вышла.

### 4.3. Занятость окна

Приходит от адаптера **только потоком**, через `onContextWindow`: `{ usedTokens, windowTokens, quality }`, где
`quality` — уже существующий `usageQuality`. Слушатель — единственный канал в контракте, способный её донести;
класть занятость ещё и в каждый исход значило бы завести второй канал под то, что уже есть. Адаптер, не умеющий
её сообщать, получает `LOOMRAIL_ESTIMATE`, как и сказано в §5.2 — то есть `contextWindowReporting` без
`eventStream` неудовлетворимо и отвергается схемой.

**Размер окна обязан быть известен до старта сессии.** Шаг 2 §6.1 вычисляет бюджет pack как долю от окна, то есть
до первого `onContextWindow`. Поэтому `contextWindowTokens` объявляется в `capabilities()` как статическое
свойство адаптера, а поток `onContextWindow` только уточняет занятость внутри уже известного окна. Адаптер, не
объявивший размер окна, не может быть запущен: собрать pack по неизвестному бюджету нельзя, а угадать его —
значит вернуться к тому же отказу, от которого A1 защищает.

Порог handoff в v1 — константа workspace-уровня, а не сущность-политика. Бюджетная политика заведена таблицей,
потому что её правит владелец; порог handoff править некому, и policy-объект под него был бы ручкой без
потребителя.

### 4.4. Event

`PROVIDER_SESSION_STARTED` (несёт `contentHash` и список выброшенных секций), `CONTEXT_HANDOFF_REQUESTED`,
`CHECKPOINT_PUBLISHED`, `PROVIDER_SESSION_ENDED`, `CONTEXT_FLOOR_EXCEEDED`.

Отдельного события «секции урезаны» нет: этот факт уже записан в рецепте, и дублировать его значило бы завести
два источника правды об одном.

Три новые таблицы добавляются новой миграцией; существующие миграции не редактируются.

## 5. Контракт провайдера

Это то, ради чего A1 идёт раньше A2.

Было:

```ts
ProviderInvocation = { dispatch, stageAttempt, workItem, decision };
ProviderAdapter = { capabilities, start, resume };
```

Стало:

```ts
ProviderInvocation = {
  dispatch,
  session: { id, ordinal, stageAttemptId, stage },
  contextPack, // готовый вход, больше ничего
};

ProviderAdapter = {
  capabilities: () => ProviderCapabilities,
  start: (invocation, listener) => Promise<ProviderOutcome>,
  requestHandoff: (sessionId) => Promise<void>,
};
```

Уходит не только `resume`. Уходят `decision`, `workItem` и `stageAttempt`: Decisions теперь секция pack, бриф —
секция pack. Входная поверхность адаптера сжимается до «pack плюс идентификаторы для корреляции». Адаптер
физически не может собрать контекст по-своему, а значит и разойтись с тем, что записано в рецепте.

`stage` в `session` оставлен сознательно: выбор модели и набора инструментов — законная работа A2, и её надо чем-то
параметризовать.

`WorkflowDispatchMode = START | RESUME` сохраняется: на уровне пайплайна различие осмысленно. Исчезает оно только
на границе адаптера.

### 5.1. Слушатель сессии

```ts
ProviderSessionListener = {
  onContextWindow: (usage) => void,
  onCheckpoint: (draft) => void,
};
```

Оба метода следуют из уже принятых решений, а не добавлены на будущее. Без потока занятости Loomrail узнаёт её
только после конца сессии, и D6 деградирует до чисто реактивного. Без промежуточной публикации checkpoint падение
процесса теряет всю сессию, а не хвост, и D2 теряет смысл.

Адаптеры без `eventStream` отдают единственный checkpoint в исходе. Это работает, просто хуже, и разница честно
выражена в `capabilities`.

### 5.2. Capabilities и исходы

`resume` уходит; добавляются `contextWindowReporting` и `checkpointOnRequest`. Если провайдер не умеет сообщать
занятость, Loomrail оценивает сам и помечает `LOOMRAIL_ESTIMATE`.

Два новых исхода: `HANDED_OFF` (свернулся по просьбе, checkpoint внутри) и `CONTEXT_EXHAUSTED` (упёрся сам,
checkpoint может отсутствовать).

### 5.3. Переименование

`mockProviderOutcomeSchema` → `providerOutcomeSchema`, `applyMockProviderOutcomeCommand` →
`applyProviderOutcomeCommand`, и связанные типы. Механическая правка, покрытая типами и тестами.

Оставить «Mock» в имени провайдеро-нейтрального контракта, который в A2 будут реализовывать живые адаптеры, —
ровно тот случай, когда временное имя закрепляется навсегда.

## 6. Поток исполнения

### 6.1. Старт сессии

Одинаково для первой и для всех последующих:

1. Loomrail берёт `ContextPackSpec` из стадии шаблона и читает `ContextSources` **одним согласованным
   снимком**. Читать источники вразнобой нельзя: рецепт фиксирует `sourceVersion` каждой секции, и если между
   чтениями что-то сдвинулось, рецепт описывает pack, которого не существовало.
2. Собирает pack с бюджетом `budgetTokens = windowTokens × maxPackShare`, где `windowTokens` объявлен
   адаптером (§4.3). Доля, а не всё окно: pack, занявший окно целиком, оставляет агенту ноль места на работу.
3. Если обязательные секции не влезли — `CONTEXT_FLOOR_EXCEEDED`, HARD-пауза, Human Request. Сессия не стартует.
4. Одной транзакцией: `ProviderSession(ordinal, RUNNING)` + `ContextPackRecipe` + `PROVIDER_SESSION_STARTED`.
5. `adapter.start(invocation, listener)`.

### 6.2. Во время сессии

- `onContextWindow` — занятость сохраняется; при первом пересечении порога пишется
  `CONTEXT_HANDOFF_REQUESTED` и вызывается `adapter.requestHandoff()`. Сессия помечается сворачивающейся, порог
  повторно не срабатывает.
- `onCheckpoint` — `Checkpoint` и `CHECKPOINT_PUBLISHED` одной транзакцией.

Оба обработчика вызываются, пока `start()` ещё не разрешился, поэтому у обоих есть гонка с концом сессии:

- `requestHandoff` идемпотентен и безопасен для уже завершившейся сессии. Порог мог пересечься ровно в момент,
  когда агент и так закончил.
- Неудачная запись checkpoint не может быть проглочена: агент считает, что опубликовал его, а следующий pack
  соберётся без него. Отказ записи завершает сессию с `endReason: INTERRUPTED` и оставляет её непродуктивной, то
  есть попадает под §6.5, а не растворяется в логе.

### 6.3. Конец сессии

| Исход               | Что дальше                                                           |
| ------------------- | -------------------------------------------------------------------- |
| `COMPLETED`         | существующая обработка стадии                                        |
| `HANDED_OFF`        | сессия `ENDED/HANDOFF` → §6.1 с `ordinal + 1`, тот же `StageAttempt` |
| `CONTEXT_EXHAUSTED` | то же, но потеря хвоста видна: за интервал нет ни одного checkpoint  |
| отказы              | существующая обработка                                               |

### 6.4. Восстановление после рестарта становится тем же механизмом

`decideRecoverInterruptedWorkflow` сейчас помечает осиротевшую попытку `INTERRUPTED`. Теперь осиротевшая сессия
помечается `ENDED/INTERRUPTED`, а продолжение — обычный §6.1 от последнего checkpoint.

Отдельного пути восстановления не появляется: рестарт демона и исчерпание контекста — один и тот же случай
«сессии больше нет, состояние есть».

### 6.5. Ограничители цикла

Существующий и косвенный: бесконечная череда сессий упрётся в `maxEstimatedTokens` и HARD-паузу. Срабатывает
поздно.

Прямой, вводимый этим спеком:

> Сессия, не опубликовавшая ни одного checkpoint, считается непродуктивной. Две непродуктивные подряд — HARD-пауза
> и Human Request.

Счётчик хранится на `StageAttempt`, а не в памяти демона, и сбрасывается любой сессией, опубликовавшей хотя бы
один checkpoint. Держать его в памяти нельзя: §6.4 делает рестарт демона обычным концом сессии, и счётчик в
памяти обнулялся бы ровно тем событием, от которого он должен защищать.

Это ловит настоящий сценарий отказа: pack подобрался так близко к окну, что порог пересекается сразу после
старта, агент сворачивается не начав, и Loomrail пересобирает то же самое. Без ограничителя это выглядит как
работающая система, которая жжёт бюджет и не двигается.

## 7. Отказы и деградация

**Просьба свернуться проигнорирована.** `requestHandoff` — просьба, а не команда. После
`CONTEXT_HANDOFF_REQUESTED` заводится крайний срок; по его истечении сессия обрывается жёстко с
`endReason: CONTEXT_EXHAUSTED` и записью, что срок вышел. Хвост теряется, но в аудите это отличимо от случая,
когда агент действительно упёрся.

**Провайдер не умеет сворачиваться** (`checkpointOnRequest: false`). Превентивный рез недоступен, остаётся
реактивная ветвь. Способность объявлена в `capabilities`, и Task Cockpit обязан показывать, что для этого
провайдера потеря хвоста штатна.

**Оценка размера промахнулась.** При `LOOMRAIL_ESTIMATE` pack может быть признан влезающим, а провайдер его
отвергнет. Сессия завершается отказом, `maxPackShare` для следующей сессии в рамках этого attempt снижается на
фиксированный шаг, и это записывается. Один автоматический повтор, дальше — Human Request. Подбирать долю
бесконечно и вслепую система не должна.

**Checkpoint пришёл невалидным.** Валидируется схемой на входе. Отклонённый checkpoint не сохраняется и порождает
Event, то есть сессия остаётся непродуктивной со всеми последствиями §6.5. Молча принять полу-checkpoint нельзя:
на нём строится следующий pack.

**Смена провайдера посреди `StageAttempt`.** Из дизайна следует: pack собран из состояния Loomrail и
провайдеро-нейтрален, `ProviderSession` — единица исполнения, а не идентичности. Сессия N+1 может открыться
другим адаптером. Это заявленное свойство PD-008 и потому вынесено в критерии приёмки (§9), а не оставлено
примечанием.

## 8. Безопасность

Checkpoint — вывод провайдера, то есть по AGENTS.md недоверенный вход. Новое здесь то, что он попадает в pack
следующей сессии и переживает смену провайдера.

**Угроза (оценка High).** Появляется канал, которого раньше не было: скомпрометированный или сбитый агент пишет в
checkpoint текст, управляющий следующей сессией, а Loomrail сам доставляет его туда — надёжно и через границу
смены провайдера. Канал устойчивый, пересекает границу доверия и невидим для владельца, если checkpoint не
показывать.

**Смягчение в дизайне:**

- checkpoint структурирован и валидируется схемой, а не является свободным блобом;
- в pack он рендерится явно отделённым как недоверенные данные, а не как инструкции;
- полный текст checkpoint виден владельцу в Task Cockpit.

`docs/security/THREAT-MODEL.md` обновляется вместе с реализацией, с проверкой на High, как требует AGENTS.md.

## 9. Критерии приёмки

| Уровень                      | Что проверяется                                                                   |
| ---------------------------- | --------------------------------------------------------------------------------- |
| `context-assembly` unit      | детерминизм байт-в-байт, порядок урезания, пол обязательных секций                |
| `workflow-engine` unit       | `validateContextPackSpec`: ординалы, дубли, отсутствие обязательной секции        |
| `domain` unit                | порог → handoff; вторая непродуктивная сессия → HARD-пауза; идемпотентность       |
| `persistence-sqlite` integr. | атомарность «сессия + рецепт + Event»; миграция шаблона v2→v3; осиротевшая сессия |
| `daemon` integration         | полный цикл: сессия 1 → порог → checkpoint → сессия 2 продолжает от checkpoint    |
| `e2e`                        | владелец видит одну идущую стадию с несколькими сессиями, а не череду падений     |

Строка `e2e` зависит от представления вложенности «attempt → сессии», форма которого отложена в §11.4. План
обязан поставить это решение раньше теста, иначе критерий окажется непроверяемым в момент, когда до него дойдёт
очередь.

Два теста делают заявленные свойства проверяемыми, а не декларируемыми:

- **Рецепт воспроизводит pack.** Пересборка по сохранённому рецепту из тех же immutable-источников даёт тот же
  хеш. Без этого теста аудит из D7 остаётся обещанием.
- **Смена провайдера посреди `StageAttempt`.** Сессия 1 одним mock-адаптером, сессия 2 другим, работа
  продолжается.

Mock-провайдер получает настоящие способности: растущая занятость, публикация checkpoint, игнорирование
`requestHandoff` (для проверки крайнего срока), невалидный checkpoint, стена. Это работа тестового двойника, а не
декорация.

## 10. Non-goals

- Живые адаптеры Codex и Claude Code — A2.
- Чтение рабочего дерева и диффы в pack — E1. Вместе с ними встанет вопрос, что из диффа допустимо класть в
  SQLite: §8.3 запрещает попадание секретов, а diff может принести значение из `.env`. Проектировать фильтрацию,
  не видя механизма чтения дерева, значит проектировать вслепую.
- Слой role playbook в цепочке §8.2 — A3. Форма слоя фиксируется здесь (D4), заполнение — там.
- Параллельные агенты и squads — A3.
- Предложение декомпозиции WorkItem при переполнении ядра — будущее уточнение D8.
- Перенос истории диалога в любом виде. Это прямо исключено PD-008.

## 11. Вопросы для implementation plan

Не влияют на контракты, но требуют решения при планировании:

1. Численные значения `maxPackShare`, порога handoff, крайнего срока `requestHandoff` и шага снижения доли.
   Подбираются на mock и выносятся в одно место как именованные константы.
2. Способ оценки размера при `LOOMRAIL_ESTIMATE`: приблизительная оценка по длине или отдельный счётчик.
3. Порядок работ внутри A1: переименование `Mock*` → `Provider*` отдельным шагом до основной работы или вместе с
   изменением контракта.
4. Представление вложенности «attempt → сессии» в Task Cockpit. D5 требует, чтобы она была видна, но форма — за
   дизайном UI.
