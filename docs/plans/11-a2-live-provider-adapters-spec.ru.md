## 1. Задача

Сегодня в дереве один провайдер — синтетический двойник. Контракт адаптера писался под него, и финальное
ревью A1 назвало четыре места, где это видно. A2 заменяет двойника двумя живыми адаптерами и чинит эти
четыре места об реальность, а не об догадку.

Работа стоит **перед** E1, то есть до того, как у продукта появится доступ к файловой системе и Git под
permission contract. Это не оплошность порядка: все четыре дыры контракта лежат в протоколе между демоном и
дочерним процессом, и ни одна из них не требует репозитория. Чинить названное дешевле, чем искать неназванное.

## 2. Что установлено пробными запусками, а не прочитано во флагах

Всё ниже получено запуском настоящих CLI на машине владельца. Каждое утверждение здесь несущее: на нём стоит
хотя бы одно решение §3.

**Codex `codex exec`:**

- `--json` печатает события JSONL в stdout;
- поток: `thread.started` (несёт `thread_id`) → `turn.started` → `item.completed` → `turn.completed`;
- **`turn.completed` несёт настоящий расход**: `{ input_tokens, cached_input_tokens, output_tokens,
reasoning_output_tokens }`;
- **отказывается запускаться вне доверенного каталога**: «Not inside a trusted directory and
  `--skip-git-repo-check` was not specified»;
- **читает stdin даже при позиционном промпте** («Reading additional input from stdin…») и виснет, если stdin
  не закрыт;
- `--output-schema <FILE>` задаёт форму финального ответа, `-C/--cd` — рабочий каталог, `-s/--sandbox` —
  политику песочницы;
- **не имеет** ни лимита ходов, ни лимита бюджета, ни таймаута, ни какого-либо канала внутрь идущей сессии.

**Claude Code `claude -p`:**

- `--output-format stream-json` даёт поток; `system/init` несёт `session_id`, модель, `cwd`, `permissionMode`,
  список инструментов и MCP-серверов; `assistant` несёт сообщение с `usage`; `result` несёт `usage`,
  `modelUsage`, `num_turns`, `stop_reason`, `permission_denials` и **`total_cost_usd`**;
- `--max-budget-usd` ограничивает трату средствами самого CLI;
- `--input-format stream-json` заявлен как поток **внутрь** сессии, `--replay-user-messages` подтверждает
  доставку впрыснутого сообщения — то есть путь спроектирован под программное управление;
- `--permission-mode plan` даёт режим без правок;
- **отказ авторизации приезжает как `subtype: "success"` при `is_error: true`** и тексте
  «Not logged in · Please run /login». Адаптер, ветвящийся по `subtype`, записал бы неудачный логин
  завершённой сессией;
- **в потоке едут события хуков пользователя** — `hook_started`, `hook_response` со `stdout` и `stderr`
  внутри.

**Не проверено.** Потоковый stdin у Claude (`--input-format stream-json`) не проверен: CLI в окружении, где
велась разведка, не авторизован. Это единственное место, где дизайн опирается на документацию флага, и §7
фиксирует запасной вариант.

## 3. Принятые решения

### D1 — До E1 адаптер не касается репозитория, и обеспечивают это сами CLI

Codex: `-C <пустой временный каталог>` + `-s read-only` + `--skip-git-repo-check`.
Claude: `--permission-mode plan` и тот же пустой каталог рабочим.

**Почему.** Запрет, выраженный тем, что мы «просто не дадим путь», не является запретом: агент способен
дойти до файлов сам. Оба CLI имеют собственные механизмы ограничения, и опереться на них честнее, чем на
собственную аккуратность.

**Принятая цена.** До E1 живой адаптер обслуживает только стадии, которым не нужен репозиторий (§4).

### D2 — Симметрии между адаптерами не добиваемся

`capabilities()` объявляет то, что CLI действительно умеет, и адаптеры выходят с разными способностями.

**Почему.** AD-005 требует именно этого, а §7 спека A1 уже написан под `checkpointOnRequest: false` как под
объявленное свойство, а не аварию. Разведка показала, что асимметрия резкая: у Claude есть канал внутрь
сессии и лимит бюджета, у `codex exec` нет ни того, ни другого. Достраивать Codex до симметрии значило бы
писать обёртку, которая имитирует способность, которой нет.

**Принятая цена.** Владелец видит два провайдера с разным поведением. Task Cockpit обязан это показывать —
это уже требование §7 A1.

### D3 — Одна `ProviderSession` — один запуск CLI; их собственный resume не используется

Ни `codex resume`, ни `claude --resume`.

**Почему.** D1 спека A1: «handoff — единственный способ запуска», продолжение это новая сборка из durable
state, а не продолжение диалога. Использовать resume провайдера значило бы завести второй путь исполнения,
который A1 сознательно убрал.

**Следствие.** `thread_id` Codex и `session_id` Claude сохраняются только для корреляции в аудите.

### D4 — Расход токенов приходит из собственного потока CLI и имеет качество `ACTUAL`

**Почему.** BD-002 требует различать actual, provider estimate и loomrail estimate. Оба CLI сообщают факт, а
не оценку, поэтому `usageQuality: "ACTUAL"` здесь заслужен. Это закрывает дыру §6.5 A1: бюджетный ограничитель
впервые получает вход, к которому его можно подключить.

**Занятость окна** вычисляется как `input_tokens / contextWindowTokens`, где знаменатель объявлен адаптером
статически (§4.3 A1). У Codex `input_tokens` после хода и есть текущий размер контекста.

**Принятая цена.** Отчёт приходит на границе хода, а не непрерывно. §6.2 A1 это и предполагает: рез
происходит в первой точке после порога, а не ровно на нём.

### D5 — `abortSession` убивает дочерний процесс

**Почему.** Это единственный пункт из четырёх, который у mock был принципиально нечестен: его `abortSession`
резолвился, ничего не останавливая. Дочерний процесс останавливается по-настоящему, и `abortSession`
резолвится только после того, как процесс подтверждённо завершился.

**Порядок:** сигнал завершения, крайний срок, затем безусловное убийство. Крайний срок именованной константой.

### D6 — MCP не используется

**Почему.** Он вытащил бы C1 вперёд через весь утверждённый порядок и открыл бы входящую границу доверия,
которую threat model не оценивала. Промежуточная публикация checkpoint решается средствами самих CLI (§6, §7)
или честно объявляется отсутствующей.

### D7 — Сырой поток провайдера недоверенный и проходит redaction до записи

**Почему.** AGENTS.md относит вывод провайдера к недоверенному входу, а SD-003 требует redaction на
logs/output/artifacts. Разведка добавила конкретики: в потоке Claude едут `stdout` и `stderr` **хуков
пользователя**, то есть произвольный текст с его машины, который Loomrail иначе записал бы себе в диагностику.

### D8 — Живой адаптер объявляет, какие стадии он может обслуживать

`capabilities()` дополняется списком стадий. Диспетчер не отправляет стадию адаптеру, который её не
обслуживает.

**Почему.** Без этого до E1 адаптер получит IMPLEMENT, не сможет ничего изменить, вернёт текст и будет выглядеть
работающим. Это ровно «контрол без поведения за ним».

**Принятая цена.** Появляется поле, у которого после E1 останется меньше работы. Дешевле, чем стадия, которая
делает вид.

## 4. Что адаптеры делают до E1

Обслуживаются стадии, которым достаточно собранного контекст-пака и текста на выходе:

- **DISCOVERY** — уточнение задачи, вопросы владельцу, предложение объёма;
- **PLAN** — план из брифа, решений и evidence;
- **REVIEW** — ревью диффа, **поданного секцией пака**, а не прочитанного с диска.

Не обслуживаются: IMPLEMENT, QA и всё, что требует рабочего дерева. Для них диспетчер продолжает использовать
mock, пока не придёт E1.

## 5. Изменения контракта

```text
ProviderId = "MOCK" | "CODEX" | "CLAUDE_CODE"

ProviderCapabilities += {
  provider: ProviderId            // было z.literal("MOCK")
  stages: WorkflowStage[]         // D8
  costReporting: boolean          // умеет ли сообщать стоимость в валюте
}

ProviderSessionListener += {
  onUsage: (usage: ProviderUsage) => void
}

ProviderUsage = {
  inputTokens, outputTokens, cachedInputTokens?, reasoningOutputTokens?,
  costUsd?: number,               // только там, где CLI сообщает
  quality: usageQuality           // "ACTUAL" для обоих живых адаптеров
}
```

`onUsage` отделён от `onContextWindow` намеренно: занятость окна и потраченные деньги — разные величины с
разными потребителями. Занятость ведёт к handoff, расход — к бюджетным порогам BD-001 и к HARD-паузе.
Складывать их в один канал значило бы, что потребитель одного обязан разбирать другой.

## 6. Адаптер Codex

Запуск: `codex exec --json --skip-git-repo-check -C <tmp> -s read-only --output-schema <checkpoint.json>`,
stdin **закрыт**, промпт — собранный контекст-пак.

| Способность              | Значение | Основание                                       |
| ------------------------ | -------- | ----------------------------------------------- |
| `eventStream`            | `true`   | JSONL из `--json`                               |
| `contextWindowReporting` | `true`   | `turn.completed.usage.input_tokens`             |
| `usageReporting`         | `true`   | там же                                          |
| `costReporting`          | `false`  | стоимости в потоке нет                          |
| `checkpointOnRequest`    | `false`  | канала внутрь одноразового `exec` не существует |
| `interrupt`              | `true`   | убийство процесса                               |

Checkpoint — финальный ответ по `--output-schema`, форма задаётся схемой `checkpointDraftSchema`. Один на
сессию.

**Превентивного реза у этого адаптера нет, и это надо сказать прямо.** `requestHandoff` — no-op, что
объявлено. Крайний срок Loomrail остаётся, но он не заменяет рез: убитый процесс **не успевает напечатать
финальный ответ**, то есть срабатывание крайнего срока стоит всего checkpoint-а сессии, а не её хвоста. Один
рычаг до старта у нас всё же есть — доля окна под пак: чем меньше пак, тем позже сессия упрётся в стену. Но
это смещение вероятности, а не гарантия, и выдавать его за рез нельзя.

Следствие, которое обязано быть видно владельцу: **для Codex потеря хвоста штатна**, ровно как §7 A1 и
предписывает показывать при `checkpointOnRequest: false`. Если это окажется неприемлемо на практике, честных
выходов два, и оба выходят за A2: `codex app-server`/`mcp-server` вместо `exec` — но это C1, — либо
периодическая публикация из самого агента, для чего нужен канал, которого у `exec` нет.

## 7. Адаптер Claude Code

Запуск: `claude -p --output-format stream-json --verbose --permission-mode plan --no-session-persistence
--max-budget-usd <лимит> --json-schema <checkpoint.json>`, рабочий каталог — пустой временный.

| Способность              | Значение | Основание                                        |
| ------------------------ | -------- | ------------------------------------------------ |
| `eventStream`            | `true`   | `--output-format stream-json`                    |
| `contextWindowReporting` | `true`   | `usage` в `assistant` и `result`                 |
| `usageReporting`         | `true`   | там же                                           |
| `costReporting`          | `true`   | `total_cost_usd`                                 |
| `checkpointOnRequest`    | см. ниже | зависит от проверки `--input-format stream-json` |
| `interrupt`              | `true`   | убийство процесса                                |

**Единственное непроверенное место дизайна.** Если `--input-format stream-json` действительно позволяет
впрыснуть сообщение в идущую сессию и `--replay-user-messages` подтверждает доставку, то `requestHandoff`
реализуется впрыском просьбы свернуться, `checkpointOnRequest: true`, и превентивный рез из §6.2 A1 работает
как задумано. **Если не подтвердится** — способность объявляется `false`, и адаптер ведёт себя как Codex:
ограничение до старта плюс финальный checkpoint. План реализации обязан поставить эту проверку первой
задачей, до всего, что от неё зависит.

**Разбор исхода идёт по `is_error`, а не по `subtype`.** Установлено разведкой: отказ авторизации приезжает
как `subtype: "success"` с `is_error: true`. Адаптер, доверившийся `subtype`, записал бы неудачный логин
успешной сессией — и §6.5 A1 не сработал бы, потому что «успешная» сессия не считается непродуктивной.

**`--max-budget-usd` — настоящий ограничитель.** Он выставляется из остатка бюджета WorkItem, и исход
`BUDGET_LIMIT_REACHED` перестаёт быть оценкой Loomrail.

## 8. Остановка и жизненный цикл процесса

Порядок при `abortSession` и при закрытии демона: сигнал завершения → крайний срок → безусловное убийство.
`abortSession` резолвится только после подтверждённого выхода процесса.

A1.5 сознательно оставил `stop()` не ждущим, потому что у mock нечего было не дождаться. С живым адаптером
ждать есть чего, и это то самое место, куда A1.5 отложил свою третью дыру.

**Осиротевший процесс.** Если демон умер, не убив дочерний процесс, тот переживёт его. Адаптер записывает pid
рядом с `ProviderSession`, и стартовая реконсиляция убивает то, что осталось, прежде чем считать сессию
завершённой.

## 9. Отказы и деградация

| Отказ                                | Поведение                                                                      |
| ------------------------------------ | ------------------------------------------------------------------------------ |
| CLI не установлен                    | `capabilities()` объявляет провайдера недоступным; диспетчер не назначает его  |
| CLI не авторизован                   | распознаётся по `is_error`, сессия — отказ, Human Request с текстом провайдера |
| CLI отказал вне доверенного каталога | ошибка конфигурации адаптера, не провайдера; тест закрепляет флаг              |
| Процесс завис без вывода             | крайний срок сессии, затем убийство; сессия непродуктивна по §6.5 A1           |
| Невалидный JSON в потоке             | строка отбрасывается с записью; поток продолжается                             |
| Финальный вывод не по схеме          | checkpoint отклонён, §7 A1 применяется без изменений                           |

## 10. Безопасность

Новых сетевых поверхностей нет: адаптеры запускают локальные процессы под учётной записью владельца.
Существенны три вещи.

**Никакого обхода разрешений.** SD-001 прямо запрещает автоматически включать
`dangerously-skip-permissions` и аналоги. Ни `--dangerously-skip-permissions` у Claude, ни
`--dangerously-bypass-approvals-and-sandbox` у Codex не появляются ни в одном пути кода. Это проверяется
тестом, а не соглашением.

**Секреты не попадают в промпт.** SD-002: контекст-пак собирается из durable state и не содержит значений
переменных окружения. Дочерний процесс наследует окружение владельца — это и есть механизм авторизации CLI по
AD-004, — но Loomrail ничего в него не добавляет.

**Сырой поток редактируется до записи.** D7. Конкретный повод дала разведка: `stdout` и `stderr` хуков
пользователя едут в потоке Claude.

`docs/security/THREAT-MODEL.md` получает строки про запуск дочерних процессов и про осиротевший процесс.

## 11. Критерии приёмки

| Уровень                | Что проверяется                                                              |
| ---------------------- | ---------------------------------------------------------------------------- |
| `provider-codex` unit  | разбор JSONL: усечённая строка, невалидный JSON, неизвестный тип события     |
| `provider-codex` unit  | `usage` из `turn.completed` доходит до `onUsage` и `onContextWindow`         |
| `provider-claude` unit | `is_error: true` при `subtype: "success"` распознаётся как отказ             |
| `provider-claude` unit | события хуков не попадают в записываемый поток                               |
| оба, unit              | ни один путь кода не строит команду с флагом обхода разрешений               |
| `domain`               | стадия не назначается адаптеру, не объявившему её в `stages`                 |
| `daemon` integration   | `abortSession` резолвится только после выхода процесса                       |
| `daemon` integration   | осиротевший процесс убивается стартовой реконсиляцией                        |
| ручная проверка        | одна настоящая стадия DISCOVERY на каждом провайдере, с записью потраченного |

Тесты адаптеров идут против **записанных** потоков, снятых с настоящих CLI, а не против выдуманных фикстур:
форма событий установлена разведкой и обязана оставаться проверяемой без сети и без квоты владельца.

## 12. Non-goals

- Любая запись в репозиторий, shell и Git — E1.
- IMPLEMENT и QA живым адаптером — после E1.
- MCP-подключения — C1 (D6).
- Параллельные сессии и squads — A3.
- Собственный resume провайдеров — исключено D3.
- Выбор модели и тарифная политика — отдельное решение владельца.

## 13. Вопросы для implementation plan

1. Проверка `--input-format stream-json` у Claude — первой задачей, до всего зависимого (§7).
2. Численные значения: крайний срок завершения процесса, доля бюджета на `--max-budget-usd`, размер
   ограничения сессии до старта у Codex.
3. Где хранится pid живой сессии, чтобы реконсиляция его нашла: колонка на `provider_sessions` или отдельная
   таблица.
4. Как снимаются записанные потоки для тестов и где они лежат, чтобы не попасть под SD-003.
