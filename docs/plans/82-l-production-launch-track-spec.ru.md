# L — Трек доказуемого запуска в продакшн

**Дата:** 2026-09-05

**Статус:** approved design; реализация в очереди после закрытия Dogfood Alpha contract

**Основание:** PD-007 (вторая persona), WD-005, TD-001, HD-003, SD-001, SD-002, SD-003, QD-002, QD-003, PD-016;
[B3+B2 project readiness](29-b3-b2-project-readiness-security-spec.ru.md),
[Q17 project verification gate](79-q17-project-verification-gate-spec.ru.md)

**Зависимости:** B3+B2, Q17, Q1–Q3, R1

## 1. Outcome

Разработчик без опыта запуска продукта доходит от репозитория до работающего продакшн-деплоя, не обходя ни одной
обязательной проверки, и на выходе получает не самоощущение, а **Launch Evidence Package**: снимок дерева, результат
каждого gate со ссылкой на evidence, запись подтверждения, вывод попытки деплоя, результат пробы задеплоенного
адреса и цель отката.

Трек не превращает Loomrail в CD-систему. Loomrail исполняет только то, что владелец подтвердил, и только один раз
за подтверждение. Automatic deployment остаётся запрещённым.

Существующие механизмы закрывают часть задачи и переиспользуются целиком: B3+B2 даёт статические факты о
репозитории со снимком и owner attestation, Q17 даёт измеряемое evidence от owner-approved recipes с честным
`STALE`, Q1–Q3 дают Browser QA и связывание criterion с evidence, SD-002 даёт обращение с секретами по имени.
Трек L добавляет к ним то, чего нет: окружения, релиз, необратимую попытку деплоя, пробу живого адреса и откат.

## 2. Декомпозиция

| Веха   | Результат                                                                                                        | Новые границы                        |
| ------ | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| **L1** | Readiness v2: lockfile, разделение dev/prod окружения, конфиг security headers, объявленный health-путь, аттестации бэкапа и плана отката | нет, только read-only наблюдения     |
| **L2** | Измеряемые gates: локальный запуск по owner-approved recipe плюс браузерные измерения перфоманса и рантайм-безопасности | локальные сетевые пробы              |
| **L3** | `Environment`, `Release`, обязательные gates и Launch Evidence Package без исполнения деплоя                      | новая миграция persistence           |
| **L4** | Guided Deploy v1: рецепт класса irreversible, один встроенный пресет, два подтверждения, проба, откат             | **PD-017, ROADMAP, THREAT-MODEL**    |
| **L5** | Жизнь после запуска: health check, протухание проверок, повторный прогон, порядок действий при падении            | периодические внешние пробы          |

L1 и L2 приносят пользу самостоятельно и не зависят от решения по L4. L3 не требует нового нормативного решения,
потому что ничего не исполняет. L4 не начинается до отдельного PD (§12).

## 3. Ubiquitous language

- **Environment** — именованная цель деплоя внутри Project. Закрытый словарь видов v1: `PREVIEW | PRODUCTION`.
  Хранит идентификатор и ревизию пресета, имена требуемых переменных окружения, объявленный владельцем публичный
  base URL и указатель на текущий успешный деплой.
- **Launch Preset** — versioned поставляемое описание одного класса цели: применимый набор gates, шаг сборки,
  шаблон команды деплоя, требуемые имена переменных, объявленные хосты и контракт разбора вывода.
- **Release** — неизменяемый снимок: Project, точное дерево (`HEAD`, признак dirty, digest наблюдений), выбранное
  окружение и разрешённый набор gates с их результатами. Release ничего не исполняет и не имеет состояния.
- **Launch Gate** — обязательная либо необязательная проверка, привязанная к Release. Gate не выполняет проверку
  сам: он разрешает ссылку на существующее evidence и вычисляет `PASSED | ACTION_REQUIRED | FAILED | STALE`.
- **Gate Waiver** — записанное владельцем пропускание одного waivable gate с обязательным обоснованием, действующее
  ровно на одну попытку деплоя.
- **Deployment** — одна попытка выката пары (Release, Environment). Класс irreversible.
- **Deployment Approval** — одноразовая запись подтверждения владельца, привязанная к точному кортежу §7.
- **Post-Deploy Probe** — измеренное read-only наблюдение объявленного адреса окружения после попытки.
- **Launch Evidence Package** — экспортируемый артефакт по образцу Acceptance Package.

Подтверждает деплой только authenticated owner. Provider и PM могут подготовить Release и предложить текст, но не
принимают пресет, не подтверждают деплой, не выдают waiver и не снимают gate. Это прямое следствие TD-001 и HD-003.

## 4. Принятые решения

### D1 — Release является снимком, Deployment является событием

Расширять каталог B3+B2 до деплоя нельзя. Readiness описывает свойство дерева в момент T; деплой имеет окружение,
попытку, результат и предыдущую успешную версию. Без отдельной сущности не выражается ни откат, ни история
окружений, ни ответ на вопрос «что сейчас в продакшне». `packages/project-readiness` остаётся модулем статических
наблюдений и получает от трека только новые пункты каталога уровня L1.

### D2 — Gate связывает evidence, а не реализует проверку заново

Каждый тип gate (`READINESS | VERIFICATION | MEASURED | REVIEW | QA | ACCEPTANCE | ATTESTATION`) разрешается в
ссылку на evidence, произведённое уже существующим механизмом. Второй источник истины о том, прошли ли тесты, не
появляется. Gate добавляет только правило обязательности и вычисление свежести относительно снимка Release.

### D3 — Loomrail исполняет, владелец подтверждает

Владелец видит preview точного executable, argv, рабочей директории, имени env-профиля и объявленных хостов, затем
подтверждает один раз. Loomrail запускает trusted runner. Это тот же контракт, что уже принят для verification
recipes в Q17; новым является только необратимость и присутствие продакшн-секретов.

### D4 — Подтверждение одноразовое и привязано к точному кортежу

Approval привязан к (digest снимка Release, Environment, ревизия пресета, точный argv, намерение деплоя). Изменение
любого элемента делает approval недействительным. Одно подтверждение — одна попытка. Повтор после провала требует
нового подтверждения. Планировщика у деплоя нет: Deployment не становится AgentRun и не резервируется scheduler.

### D5 — Продакшн требует предыдущего preview, хотфикс является именованным исключением

Намерение деплоя: `STANDARD | HOTFIX`.

`STANDARD` в `PRODUCTION` допускается только если тот же снимок Release уже успешно выкатился в `PREVIEW`. Первый
выкат учит, второй решает.

`HOTFIX` пропускает preview, но не подтверждение, и требует одновременно: существующего ранее успешного деплоя в это
окружение и обязательного письменного обоснования владельца. Требование предыдущего успеха даёт побочный эффект:
у хотфикса всегда есть цель отката.

### D6 — Три gate неотключаемы, остальные waivable с обоснованием

Неотключаемы даже в хотфиксе: `SECURITY_SECRET_PATHS`, `SEC_CLIENT_BUNDLE_SECRETS`, `ENV_PROD_SEPARATION`. Причина
общая: их провал необратим после публикации. Проваленный перфоманс чинится следующим деплоем; уехавший в продакшн
секрет откатить нельзя, его можно только ротировать, обычно уже после использования.

`SEC_CLIENT_BUNDLE_SECRETS` измеряется по собранному бандлу, поэтому хотфикс всё равно требует сборки. Это
осознанная цена: без сборки нельзя ни выкатить, ни доказать отсутствие секрета в том, что уедет пользователю.

Остальные gates пропускаются как `Gate Waiver` с обязательным обоснованием. Waiver действует на одну попытку, не
переносится на следующий Release, попадает в Launch Evidence Package и audit history. Успешный деплой с waiver'ами
одной транзакцией создаёт durable follow-up в Attention Inbox, а окружение показывает количество пропущенных
проверок, пока follow-up не закрыт.

### D7 — Прерванная попытка даёт `UNKNOWN`, автоповтора не существует

Запись `RUNNING` вместе с Approval выполняется одной транзакцией до запуска процесса. Startup reconciliation
переводит прерванную попытку в `UNKNOWN`, а не в `FAILED`: доехал деплой или нет, локально неизвестно. Выход из
`UNKNOWN` только через владельца; Loomrail запрашивает статус у пресета, прогоняет пробу и показывает наблюдаемое.
Повторный выкат вслепую запрещён.

### D8 — Откат не проходит gates и предлагается первым

Единственное условие отката — целевой Deployment ранее имел `SUCCEEDED` в этом окружении. Gates к откату не
применяются, потому что откат возвращает уже проверенное состояние. Откат сам является попыткой деплоя со своим
одноразовым подтверждением, а не операцией «отменить». В инцидентном сценарии UI предлагает откат первым пунктом и
хотфикс вторым.

### D9 — Вывод пресета является недоверенным входом

Разбирается только объявленный пресетом контракт вывода. Свободный поиск по произвольному тексту чужого процесса
запрещён. Нулевой exit code без разобранного адреса даёт `SUCCEEDED` с пробой в состоянии `ACTION_REQUIRED`, пока
владелец не укажет адрес вручную.

### D10 — Проба идёт только по объявленному адресу и только на чтение

Post-Deploy Probe обращается к base URL, объявленному владельцем для окружения. Произвольный адрес недопустим,
иначе Loomrail становится сканером чужих сайтов. Проба выполняет только чтение, не использует продакшн-креды для
авторизации и не выходит за объявленные маршруты. Провал пробы не откатывает автоматически: автооткат является той
же automatic deployment authority.

### D11 — Секреты по имени, сетевая политика является декларацией

Рецепт ссылается на env-профиль по имени; значения живут в macOS Keychain или Windows Credential Manager и
подставляются trusted runner в процесс, не попадая в prompt, логи и артефакты (SD-002, SD-003). Объявленные хосты
показываются владельцу как декларация намерения, а не как enforcement: AGENTS.md уже фиксирует, что worktree и
контейнер не являются полноценной песочницей, и сетевая изоляция здесь не обещается.

### D12 — Результат формулируется как снимок доказательств

Формулировки вида «Production ready» запрещены. Каноническая форма: «на снимке `<commit>`, `<дата>`: пройдено N из
M, K закрыто владельцем как неприменимое, обязательных провалов нет» плюс явный перечень того, что Loomrail не
проверял. Окружение всегда показывает возраст последней проверки и расхождение с текущим деревом.

### D13 — Провал gate превращается в Task

Любой проваленный gate одним действием становится WorkItem с готовым brief, acceptance criteria и ссылкой на
evidence. Работа проходит обычный workflow с независимым review и QA, после чего gate пересчитывается. Второй
persona нужно понимать, что сломано, а не как это чинить.

## 5. Каталог gates v2

Каталог версионируется. Пресет объявляет применимый набор; неприменимое владелец закрывает как `N/A` с
обоснованием, чтобы у статического сайта не спрашивали про бэкап базы.

### 5.1. `READINESS` — статика, L1

Существующие пункты B3+B2 сохраняются без изменений: `SECURITY_ACTIVE_CONSTITUTION`, `SECURITY_SECRET_PATHS`,
`SECURITY_ENV_IGNORED`, `SECURITY_CI_HARDENING`, `LEGAL_LICENSE`, `LEGAL_OWNER_REVIEW`, `PAYMENTS_OWNER_REVIEW`,
`ANALYTICS_OWNER_REVIEW`.

Добавляются:

| Key                             | Режим     | Что проверяется                                                                        |
| ------------------------------- | --------- | -------------------------------------------------------------------------------------- |
| `DEPS_LOCKFILE_PRESENT`         | AUTOMATED | Lockfile отслеживается Git и соответствует manifest                                     |
| `ENV_PROD_SEPARATION`           | AUTOMATED | Требуемые имена переменных объявлены полностью, прод-значения не лежат в репозитории    |
| `SECURITY_HEADERS_CONFIGURED`   | AUTOMATED | В конфигурации пресета или фреймворка объявлены security headers                        |
| `OPS_HEALTH_ENDPOINT_DECLARED`  | OWNER     | Объявлен путь health/ready либо обоснованное `N/A`                                      |
| `OPS_ROLLBACK_PLAN`             | OWNER     | Владелец подтвердил порядок действий при падении                                        |
| `OPS_BACKUP`                    | OWNER     | Владелец подтвердил порядок резервного копирования данных либо обоснованное `N/A`       |

### 5.2. `VERIFICATION` — Q17, существует

Owner-approved build/test/lint/integration/E2E recipes на точном дереве. Новых механизмов не требуется.

### 5.3. `MEASURED` — L2

Приложение поднимается локально по owner-approved recipe, измерения выполняет существующий `packages/browser-qa`.

| Key                        | Что измеряется                                                                    |
| -------------------------- | --------------------------------------------------------------------------------- |
| `PERF_WEB_VITALS`          | LCP ≤ 2.5s, INP ≤ 200ms, CLS ≤ 0.1; медиана из 3–5 прогонов против дрожания        |
| `PERF_BUNDLE_BUDGET`       | Суммарный вес скриптов против объявленного бюджета                                 |
| `SEC_RESPONSE_HEADERS`     | Фактические заголовки ответа, а не объявленные в конфиге                           |
| `SEC_UNAUTHENTICATED_ROUTES` | Объявленные приватные маршруты отвечают 401/403 без сессии                       |
| `SEC_CLIENT_BUNDLE_SECRETS` | В собранном клиентском бандле отсутствуют секретоподобные строки                  |
| `DEPS_AUDIT`               | Известные уязвимости зависимостей по lockfile                                      |

`SEC_CLIENT_BUNDLE_SECRETS` и `SEC_UNAUTHENTICATED_ROUTES` покрывают класс отказов, который статикой не виден и
который стабильно воспроизводится в публично задеплоенных AI-сгенерированных приложениях (§13).

### 5.4. `REVIEW`, `QA`, `ACCEPTANCE`, `ATTESTATION`

Существующие механизмы R1, Q1–Q3 и owner attestations связываются с Release без изменения их семантики.

## 6. Пресет, рецепт и проба

Launch Preset объявляет: применимый набор gates; шаг сборки, переиспользующий уже принятый verification recipe, если
он есть; шаблон команды деплоя с точным executable и argv; рабочую директорию; таймаут и предел объёма вывода; имена
требуемых переменных; объявленные хосты; контракт разбора вывода; способ запроса статуса деплоя; способ отката.

Deployment не является AgentRun и не расходует provider budget; его ограничивают объявленные таймаут и предел
вывода, а не BD-001.

В v1 поставляется один встроенный пресет для самого частого пути второй persona: фронтенд с serverless-функциями.
Остальные цели добавляются пресетами, не затрагивая ядро. SSH, VPS, контейнерные раскатки и мобильные сторы в v1 не
входят.

Post-Deploy Probe проверяет: доступность адреса, валидность TLS, фактические заголовки, Web Vitals на живом деплое,
ответ 401/403 на объявленных приватных маршрутах, отсутствие секретоподобных строк в отданном клиентском бандле и
ответ health-эндпоинта.

## 7. Состояния, восстановление и persistence

```text
PENDING_APPROVAL -> APPROVED -> RUNNING -> SUCCEEDED
                                        -> FAILED
                                        -> UNKNOWN
                              SUCCEEDED -> ROLLED_BACK
```

Release состояния не имеет. Одной транзакцией сохраняются: текущее состояние Deployment, audit Event и, при
необходимости, durable follow-up — как требует AGENTS.md. Переходы проверяются доменом; домен не читает файловую
систему и не знает про SQLite. Новая миграция добавляет `Environment`, `Release`, `LaunchGateResult`, `GateWaiver`,
`Deployment`, `DeploymentApproval` и `PostDeployProbe`.

Approval-кортеж: `(releaseSnapshotDigest, environmentId, presetRevision, argvDigest, intent)`.

## 8. Security и privacy delta

- продакшн-секреты не хранятся Loomrail; используются имена профилей и OS-хранилище (SD-002);
- вывод попытки и пробы ограничен по объёму и проходит redaction перед сохранением;
- проба выполняет только чтение и только по объявленному владельцем адресу (D10);
- вывод пресета обрабатывается как недоверенный вход и валидируется в рантайме (D9);
- сетевая политика рецепта декларируется, но не обещается как изоляция (D11);
- Deployment недоступен агенту: подтверждение, waiver и откат требуют authenticated owner;
- перед L4 обновляется `docs/security/THREAT-MODEL.md`, а Critical/High угрозы получают верификацию.

## 9. UI и объяснимость

Маршрут `Project → Launch` продолжает существующий `Project → Readiness`. Прогресс подаётся тремя шагами —
проверить, выкатить в preview, выкатить в продакшн, — и на каждом показывается только то, что мешает именно этому
шагу. Каждый провал объясняется последствием на обычном языке, а не термином, и предлагает одно конкретное
действие либо создание Task по D13. Статус не кодируется цветом: провал, waiver и `N/A` различимы без него. Light и
dark темы равноправны, клавиатурная работа и видимый фокус реализуются сразу.

## 10. Non-goals

- CI-хостинг и замена GitHub Actions;
- управление аккаунтами хостинга, доменами и платёжными провайдерами от имени владельца;
- security-аудит, юридическая консультация и любое обещание production safety;
- automatic deployment, автоматический повтор и автоматический откат;
- сканирование произвольных адресов;
- SSH/VPS, контейнерные раскатки и мобильные сторы в v1;
- постоянный мониторинг с SLA; L5 ограничен owner-инициированными и явно настроенными проверками.

## 11. Acceptance трека

- [ ] владелец проходит от репозитория до успешного продакшн-деплоя, не обходя обязательных gates;
- [ ] каждый gate в Launch Evidence Package связан с конкретным evidence и снимком дерева;
- [ ] изменение дерева делает подтверждение недействительным, а evidence — `STALE`;
- [ ] `STANDARD` в продакшн без предыдущего успешного preview того же снимка невозможен;
- [ ] `HOTFIX` требует предыдущего успешного деплоя и обоснования, создаёт follow-up и виден в окружении;
- [ ] три неотключаемых gate не обходятся ни хотфиксом, ни waiver'ом;
- [ ] рестарт daemon во время `RUNNING` даёт `UNKNOWN` и не порождает второй попытки;
- [ ] откат возвращает предыдущий успешный деплой и не требует прохождения gates;
- [ ] секреты не попадают в логи, артефакты, prompt и Git;
- [ ] проба отказывается работать с адресом, не объявленным для окружения;
- [ ] маршрут проверен на macOS и Windows, включая пути с пробелами и не-ASCII;
- [ ] RU/EN, light/dark, клавиатура и узкий viewport проверены.

## 12. Нормативные изменения, требуемые до L4

L1–L3 не меняют утверждённых границ. До начала L4 требуется отдельное владельческое решение:

1. новый PD (предположительно PD-017): guided owner-confirmed deploy разрешён, automatic deployment остаётся
   запрещённым;
