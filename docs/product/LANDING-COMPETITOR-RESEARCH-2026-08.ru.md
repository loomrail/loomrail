# Исследование лендингов локальных AI-agent tools

Дата: 30 августа 2026 года

## Задача

Проверить, как близкие по аудитории продукты объясняют ценность, установку и границы продукта, а затем использовать
только подтверждённые паттерны для нового лендинга Loomrail. Источники ниже — официальные сайты и репозитории
продуктов; рекламные подборки и пересказы не использовались.

## Что делают сильные примеры

### Agent Orchestrator

[Официальный сайт Agent Orchestrator](https://aoagents.dev/) начинает с результата для пользователя — меньше ручного
контроля за агентами и больше готовой работы — и сразу показывает реальную поверхность продукта. Команда Homebrew
находится рядом с первым экраном, а не спрятана в документации.

Вывод для Loomrail: на первом экране назвать конкретный результат — проверяемая поставка и решение владельца — и дать
короткий путь к запуску.

### Mission Control

[Официальный README Mission Control](https://github.com/builderz-labs/mission-control/blob/main/README.md) явно
маркирует alpha-статус, отдельно показывает локальный запуск и Docker-вариант и организует документацию по задачам
пользователя. Ограничения не вынесены в мелкий шрифт.

Вывод для Loomrail: pre-alpha и текущие границы должны стоять рядом с CTA; документация должна начинаться с quick
start, а затем вести к своему репозиторию, providers, recovery и security.

### amux

[Официальный README amux](https://github.com/mixpeek/amux) разделяет установку на Homebrew, `pipx`/`uv` и запуск из
исходников, а также показывает способ попробовать продукт без постоянной установки. Требования и security caveats
стоят рядом с командами.

Вывод для Loomrail: один рекомендуемый npm-путь должен быть главным, а global install и source build — вторичными;
Node.js, поддерживаемые ОС и loopback-модель должны быть видны до запуска команды.

### Vibe Kanban

[Официальный README Vibe Kanban](https://github.com/BloopAI/vibe-kanban) формулирует проблему на языке пользователя,
даёт короткую команду запуска и сразу предупреждает, что CLI coding-agent должен быть установлен и авторизован.

Вывод для Loomrail: не продавать «оркестрацию» как абстракцию. Объяснять механику: задача, evidence, owner Decision,
локальное состояние. Отдельно сказать, что mock-run не требует provider quota, а live-run требует готовый CLI.

## Что переносим в Loomrail

- Первый экран отвечает на три вопроса: что изменится, где работает продукт и кто принимает результат.
- Реальный Workbench остаётся главным доказательством; выдуманные метрики, отзывы и logo wall не добавляются.
- Установка строится как короткая последовательность: установить пакет, запустить, пройти безопасный mock-route.
- Один рекомендуемый способ установки визуально доминирует; альтернативы не конкурируют с ним.
- Pre-alpha, Node.js `>=24.19 <25`, macOS/Windows и отсутствие commit/push/merge видны до установки.
- Навигация по документации строится вокруг задач: Quick start, User guide, Full route, Security.
- RU и EN используют одну структуру и одинаковый объём продуктовых обещаний.

## Что сознательно не переносим

- Обещания «10×», экономии времени или количества пользователей без измерений.
- Списки поддерживаемых agents ради длины списка: возможности адаптеров должны оставаться точными.
- Скриншоты с нарисованным browser chrome, декоративные AI-градиенты и анимацию ради движения.
- Cloud, mobile, remote access, desktop installer и автоматический Git publish — этих возможностей в текущем scope нет.
- Отзывы, customer logos и сравнительные таблицы без реальных данных пользователя.

## Позиционирование

Соседние продукты чаще продают параллельный запуск агентов или удобную доску. Loomrail должен занимать более узкую и
проверяемую позицию: локальный control plane, в котором brief, критерии, запросы человеку, budgets, evidence и
acceptance переживают отдельную provider-сессию. Агент предлагает и показывает работу; итог принимает владелец.
